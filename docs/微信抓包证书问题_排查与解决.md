# 微信网页打不开 + HttpCanary 抓包证书 —— 排查与解决

> 记录时间：2026-10-30
> 设备：REDMI K90 Pro Max/ Android 17 / HyperOS 3 / KernelSU（`u:r:ksu:s0`）
> 抓包工具：HttpCanary 3.3.6（`com.guoshi.httpcanary`，targetSdk 28）
> 相关模块：TrustMeAlready 1.11（`com.virb3.trustmealready`）、LSPosed（zygisk）

---

## 一、现象

| 编号 | 现象 |
|---|---|
| P1 | LSPosed 里把 TrustMeAlready 作用域勾选微信后，微信内打开任何网页都弹「安全警告：该网站的安全证书存在问题」（如 `qq.com`、`github.com`），网页无法加载；聊天、收消息一切正常 |
| P2 | 微信旧版本时同一套配置正常，升级新版本后开始出问题 |
| P3 | 用 HttpCanary 开抓包时，微信内网页同样报证书错误 |
| P4 | HttpCanary 的根证书从未装进系统信任库（用户库、系统库都没有） |

---

## 二、根因：模块把「可信证书链」替换成了空链表

### 2.1 模块实现（jadx 反编译）

模块只有一个 hook 点，在 `initZygote` 阶段全局挂钩 `com.android.org.conscrypt.TrustManagerImpl.checkTrustedRecursive`，替换实现直接返回空 `ArrayList`：

```java
// Main.java（反编译）
arrayList.add(new XC_MethodReplacement() {
    protected Object replaceHookedMethod(XC_MethodHook.MethodHookParam p) {
        return new ArrayList();      // ← 空链表，不做任何校验
    }
});
XposedHelpers.findAndHookMethod(SSL_CLASS_NAME, null, SSL_METHOD_NAME, arrayList.toArray());
```

判定条件：方法名 == `checkTrustedRecursive` 且返回类型可赋值给 `List` 且泛型参数为 `X509Certificate`。

### 2.2 LSPosed 日志证实只挂了这一个方法

```
private java.util.List com.android.org.conscrypt.TrustManagerImpl.checkTrustedRecursive(
    X509Certificate[], byte[], byte[], String, boolean, List, List, Set) throws CertificateException
TrustMeAlready loaded! Hooked 1 methods
```

### 2.3 模块确实注入了微信的网页内核进程

```
12 × (com.tencent.mm:xweb_privileged_process_0)[com.virb3.trustmealready ...]
32 × (com.tencent.mm:appbrand1)   20 × (com.tencent.mm:patch)
```

新版微信的网页由 XWeb（pinus / Chromium）承载：
`com.tencent.mm:xweb_privileged_process_0`、`com.tencent.mm:xweb_sandboxed_process_0:com.tencent.xweb.pinus.sdk.process.SandboxedProcessService`。

### 2.4 设备 Conscrypt 实测：空链会原样流出去

从设备 `/apex/com.android.conscrypt/javalib/conscrypt.jar` 反编译 `TrustManagerImpl`：

```java
private List<X509Certificate> checkTrusted(X509Certificate[] chain, byte[] ocspData, byte[] tlsSctData,
                                          String host, String authType, boolean clientAuth) {
    ...
    return checkTrustedRecursive(chain, ocspData, tlsSctData, host, clientAuth, list, list2, set);
}
```

`checkTrusted()` 直接把递归结果返回，**空链不抛异常**。这正是模块当年能"绕过 pinning"的原因：Java/OkHttp 客户端只关心"有没有抛异常"，不看链内容。

### 2.5 Chromium 侧：空链 = 无法确认系统根

Chromium 的 `org.chromium.net.X509Util`（WebView/XWeb 的 Java 校验入口）逻辑为：

```java
boolean isIssuedByKnownRoot = false;
if (verifiedChain.size() > 0) {
    X509Certificate root = verifiedChain.get(verifiedChain.size() - 1);
    isIssuedByKnownRoot = isKnownRoot(root);   // 拿"链尾"当锚点去比对系统 CA 库
}
```

空链 → `isIssuedByKnownRoot = false`，Chromium 无法认定该连接由系统根签发 → WebView 触发 `onReceivedSslError` → 微信弹出自己的「安全警告」对话框。

### 2.6 对照实验

| 条件 | 结果 |
|---|---|
| 系统浏览器（未勾作用域）打开 `https://qq.com` | 正常 |
| 微信打开同一链接（模块在作用域内） | 必弹安全警告 |
| 微信移出作用域后打开 `https://qq.com` / `https://www.163.com` | 正常 |

## 三、为什么旧版微信正常、新版异常

| | 旧版微信 | 新版微信 |
|---|---|---|
| 网页内核 | X5 / TBS（Tencent 自研 Chromium） | XWeb（pinus，Chromium 内核，独立进程） |
| 证书校验位置 | Native（BoringSSL + 自有根证书库） | Java Conscrypt + Chromium `X509Util` |
| 受 Java Xposed hook 影响 | 否 | **是** |

微信自有通信走 MMTLS / mars native 栈，不受 Java hook 影响，所以"消息正常、只有网页坏"。

---

## 四、为什么"换个模块"也救不了微信网页

只要模块仍然把 `checkTrustedRecursive` 的返回值置空（如 `pccr10001/SSLUnpinner` 的 `RETURN_EMPTY_LIST`），Chromium 拿到的就是空链，结论不变：

> **WebView/XWeb 只认"系统信任库中的根"**（Android 7+ 应用默认 trust-anchors = system），Java 层的"信任全部"技巧对 Chromium 无效。

因此想让微信网页正常 + 同时能抓包，唯一可靠路径是：**把抓包工具的根证书装进系统信任库**。

---

## 五、解决方案：HttpCanary 根证书写入系统信任库

### 5.1 关键技术障碍（实测）

| 障碍 | 实测结论 |
|---|---|
| Android 14+ 系统证书库迁移到只读 APEX | 真正生效路径是 `/apex/com.android.conscrypt/cacerts`（145 张）；`/system/etc/security/cacerts` 另有一份副本（同样 145 张） |
| 运行期 `mount --bind` 能否生效 | **不能**。shell 内挂载后是 146 张，但 `nsenter` 进微信各进程仍是 145 —— 应用进程有独立 mount namespace |
| zygote 启动时机 | post-fs-data（zygote 之前）挂载可被所有应用继承 |

验证命令：

```sh
mount --bind /data/local/tmp/cacerts /apex/com.android.conscrypt/cacerts
echo "self=$(ls /apex/com.android.conscrypt/cacerts | wc -l)"        # 146
nsenter -t <微信pid> -m -- ls /apex/com.android.conscrypt/cacerts | wc -l   # 145（未继承）
```

> 注：设备上的 `nsenter` 是 toybox 版，命令前必须加 `--`，否则会报 `Unknown option 'bind'`。

### 5.2 证书准备

```sh
# HttpCanary CA 位置（root）
/data/data/com.guoshi.httpcanary/files/backup/HttpCanary.pem    # CN=HttpCanary Root CA，有效期至 2036-10
# 计算 Android 文件名（MD5 旧式哈希）
openssl x509 -in HttpCanary.pem -noout -subject_hash_old      # <hash>
# → 文件名 <hash>.0，内容为 PEM
```

### 5.3 模块结构（KernelSU，`/data/adb/modules/hc_cacert/`）

```
hc_cacert/
├── module.prop
├── post-fs-data.sh          # 开机早期：合并证书 + bind mount
├── service.sh               # late_start 兜底：APEX 晚挂时重试，并给已运行应用 nsenter 补挂
└── certs/<hash>.0            # 抓包工具根证书（PEM，文件名为 subject_hash_old）
```

`post-fs-data.sh` 关键逻辑（带失败保护，任何异常只写日志、不挂载）：

```sh
SRC=/apex/com.android.conscrypt/cacerts        # 不存在则退回 /system/etc/security/cacerts
BASE=$(ls "$SRC" | wc -l)                      # 145
cp -f "$SRC"/* "$WORK"/ ; cp -f "$MODDIR/certs/$CERT" "$WORK/"
NEW=$(ls "$WORK" | wc -l)
[ "$NEW" -lt "$((BASE + 1))" ] && exit 0        # 拷贝不完整 → 放弃挂载（防止把 TLS 搞坏）
chown -R 0:0 "$WORK"; chmod 644 "$WORK"/*; chcon -R u:object_r:system_file:s0 "$WORK"
mount --bind "$WORK" /apex/com.android.conscrypt/cacerts
mount --bind "$WORK" /system/etc/security/cacerts
```

### 5.4 安装步骤

**方式 A（推荐）：刷模块 zip**

`hc_cacert.zip`（项目根目录，magisk 模块格式，含 `META-INF/.../update-binary`，Magisk 与 KernelSU 通用）：

```
KernelSU 管理器 → 模块 → 从本地安装 → 选择 hc_cacert.zip → 重启
```

或命令行：

```sh
adb push hc_cacert.zip /data/local/tmp/
adb shell su -c 'sh /path/to/update-binary 3 1 /data/local/tmp/hc_cacert.zip'   # 非必需，管理器安装即可
adb reboot          # 必需
```

**方式 B：手动拷贝到模块目录**

```sh
adb push module /data/local/tmp/hc_module
adb shell su -c 'mkdir -p /data/adb/modules/hc_cacert && cp -r /data/local/tmp/hc_module/* /data/adb/modules/hc_cacert/ \
  && chown -R 0:0 /data/adb/modules/hc_cacert \
  && chmod 755 /data/adb/modules/hc_cacert/*.sh \
  && chmod 644 /data/adb/modules/hc_cacert/module.prop /data/adb/modules/hc_cacert/certs/<hash>.0'
adb reboot          # 必需
```

## 六、日常使用与维护

**必须遵守**

1. **不要再把微信勾进 TrustMeAlready**（以及任何把 `checkTrustedRecursive` 置空的模块），否则网页立即报证书错误；该模块对微信已无价值、只有副作用。
2. 微信自有通信是 MMTLS / mars native 栈（大量 `http://xxx.weixin.qq.com/mmtls/...`），装了证书也只能看到封装层；能解的是内嵌网页、小程序资源、以及走标准 TLS 的第三方域名。

**换抓包工具（Charles / Reqable / Burp / mitmproxy）**

```sh
openssl x509 -in your_ca.pem -noout -subject_hash_old      # 得到 <hash>
cp your_ca.pem /data/adb/modules/hc_cacert/certs/<hash>.0  # 可放多张
adb reboot
```

**回滚**

KernelSU 里禁用/删除 `hc_cacert` 模块后重启即可。模块只做 bind mount，未修改任何只读分区，重启后证书库自动恢复 145 张。

**排错**

- 看日志：`su -c cat /data/local/tmp/hc_cacert.log`
- 看数量：`su -c 'ls /apex/com.android.conscrypt/cacerts | wc -l'`（应为 146）
- 若为 145：检查 `/data/local/tmp/hc_ca.log` 中是否 `abort`（拷贝不完整 / APEX 未就绪）

## 七、结论与经验

1. **"信任全部证书"的 Xposed 模块与 Chromium 内核天生不兼容**：它们靠"返回空链/不抛异常"生效，而 Chromium 需要链尾是系统根。旧版微信用 X5（native 校验）所以侥幸可用，换 XWeb 后必然翻车。
2. **Android 14+ 装系统证书必须走开机挂载**：证书在只读 APEX，且应用进程有独立 mount namespace，运行期挂载不传播。
3. **权限边界**：`subject_hash_old` 命名的 PEM 才是 Android 认的格式；SELinux 上下文必须 `u:object_r:system_file:s0`。
4. **排查手法沉淀**：jadx 反编译模块 → LSPosed verbose 日志确认注入进程 → 从设备 APEX 取 Conscrypt 反编译确认空链流向 → 对照实验（浏览器 vs 微信）闭环。
